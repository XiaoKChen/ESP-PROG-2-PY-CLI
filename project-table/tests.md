- **`test_cli.py`** — CLI behavior:
  - `--version` prints the package version and exits 0.
  - `--provision-node` keeps a SOLO preset's board profile and writes the v2 block alone for other products.
  - `--read-node-config` output with and without a profile (the v2 text from a decoded record).
  - `--flash-app` resolves the base address (default `APP_BASE_ADDRESS`, `--embassy` → `EMBASSY_APP_BASE_ADDRESS`, an explicit `--app-address` wins) and passes `embassy` through to `flash_app`.
  - `--embassy` or `--app-address` without `--flash-app` exits 2 with `<flag> only applies with --flash-app.` on stderr before any `flash` / `detect` call.
  - An out-of-range app address exits 2 with one `Application flash refused: ...` line on stderr and no traceback.
  - Not covered: whole-parser handling, esptool runs.

- **`test_flasher.py`** — The SOLO and CAN-node paths through an emulated-flash esptool runner, the RA4M1 app-flash range check and metadata decision, and the bundled RA4M1 bootloader pin:
  - `flash_solo`: both presets, migrate-stock erase, app + otadata, `--after` modes, read-back mismatch, esptool failure with the hold-BOOT hint, validation before any esptool call, a failing final reset not failing the flash.
  - The no-reset steps plus the final watchdog-reset `chip-id` of every node path (`read_node_config`, both `provision_node` variants, `flash_solo`); `provision_node` with and without a profile and the node's record version; `read_node_config` (incl. a v2 profile and an erased partition).
  - The 1200-baud entry through `FakePorts`: a running board (USB serial = bare MAC) is touched once and every esptool call follows it to its ROM port (`303A:1001`, serial = MAC with colons, case-insensitive); the switch is logged; a ROM port that never appears within `NODE_ROM_PORT_TIMEOUT_S` fails before any esptool call with the hold-BOOT message; an already-ROM port, a port with no serial, a non-MAC serial or an unlisted port is used as given with no touch.
  - The bundle-version gate (`bundle_profile_version`, `release_tag_profile_version`, `read_bundle_version`) and the record version `flash_solo` writes per bundle (v2 on 1.3.0+, v1 plus a warning for the ODU on older ones); `load_solo_bundle` manifest rules; `otadata_selecting_ota0` against the bench CRC; `fetch_solo_bundle` (success, missing release, missing gh, no asset).
  - `check_app_range` (parametrized) refuses with `AppRangeError` address 0, one below `APP_BASE_ADDRESS`, a negative address, an image ending past `RA4M1_CODE_FLASH_END`, an empty image, the Embassy bootloader at the C base and one below `EMBASSY_APP_BASE_ADDRESS`; it accepts the C base, `0x8000`, an image ending exactly at code-flash end, the Embassy flag at the Embassy base, and the issue-#39 `ff.bin` case (`RA4M1_METADATA_SIZE` bytes at `RA4M1_METADATA_ADDRESS`). The error names the bootloader it would overwrite and formats a negative address without `0x-`.
  - `flash_app` raises `AppRangeError` for a below-base, oversized, empty or Embassy-at-C-base request before `_choose_raw` (probe selection) is reached.
  - `ra4m1_metadata_action`: the app flash erases the metadata block (`RA4M1_METADATA_ADDRESS`) only at the default `APP_BASE_ADDRESS`, reports "covered" when the image reaches it at any base, and "keep" at a non-default base that stops short (parametrized). `_check_metadata_sector` accepts one 2 KB flash sector and refuses a missing region or any other geometry.
  - The bundled RA4M1 bootloader: `find_default_hex()` resolves an existing file named `bootloader-uno_r4.hex`. Read with intelhex, its segments equal `BOOTLOADER_SEGMENTS` (`[(0x0, 0x3B84), (0x01010018, 0x01010034)]`) and a sha256 over the segment data in address order equals `BOOTLOADER_DATA_SHA256`, pinning it to Embedded-CAN-Bootloaders `c-cpp-ra4m1-v1.2.0` regardless of line endings. Its code segment ends at or below `APP_BASE_ADDRESS`.
  - Not covered: real esptool, a real 1200-baud touch or port listing, the real gh download, the pyOCD paths (the metadata erase itself included).
