`esp-prog2-flasher` — a `uv`-managed Python TUI/CLI for the ESP-Prog-2 debug probe.
It flashes a bootloader to a target board (Renesas RA4M1 / UNO R4 Minima) over SWD
with **pyOCD**, optionally writes a device config block (custom USB DFU manufacturer/
product names plus a per-device bootloader CAN ID pair) into the target's data flash,
can flash a PlatformIO/Arduino application `.bin` to the target's app region (`0x4000`)
over SWD, and reflashes the ESP-Prog-2's own ESP32-S3 firmware with **esptool**.

## Architecture Overview

The package is layered so the flashing logic has **no UI dependency**:

- **`flasher.py`** is the engine. It wraps **pyOCD** for the ARM target (detect the ESP-Prog-2
  CMSIS-DAP probe by VID `0x303A`/PID `0x1002`, examine an `r7fa4m1ab` core over SWD, halt/read
  the PC to tell blank from programmed, **reset-and-halt then program a `.hex`** via
  `FileProgrammer`, and optionally **write a DFU config block** to data flash `0x40101C00`
  via `FlashLoader` — enabling the RA4M1 `DFLCTL` data-flash read before verifying). It also
  programs a raw **application `.bin`** with `flash_app()` at `APP_BASE_ADDRESS = 0x4000`
  (overridable) using `FileProgrammer(..., chip_erase="sector")`, so only the app pages are
  erased and the bootloader below is preserved. It drives **esptool** (subprocess or frozen-build
  shim) for the ESP-Prog-2's own ESP32-S3 firmware, plus **pyserial** port detection and a
  **truststore**-backed official-image download. Backends are imported lazily; bundled
  `hex/`/`firmware/` assets resolve from a PyInstaller `_MEIPASS` bundle first, then by walking
  up from the package/CWD.
- **`dfu_config.py`** encodes the frozen 80-byte v2 DFU config block — manufacturer/product names
  plus a per-device bootloader CAN ID pair (`boot_cmd_id`/`boot_reply_id`, `0xFFFF` = unset). Its
  layout and CRC must stay in lockstep with the bootloader's `src/boot/dfu_config.*`. `DEVICE_CAN_IDS`
  is the single source of truth mapping known devices to fixed CAN ID pairs; `DEVICE_NAMES` derives
  from its keys.
- **`app.py`** is a **Textual** TUI (`FlasherApp`) calling `flasher` from `@work(thread=True)`
  workers; it never touches USB/serial directly. It lays out three panels — target (bootloader
  hex, manufacturer/product rows, a "Custom…" device option, editable/locked boot-CAN-ID inputs,
  Detect/Flash-target), ESP-Prog-2 firmware, and an "Application (RA4M1 over SWD)" panel (app `.bin`
  picker + Flash app). Its `FilePickerScreen` is suffix-generalized and shared by the `.hex` and
  `.bin` pickers.
- **`cli.py`** is the single entry point: bare invocation launches the TUI; flags (`--detect`,
  `--flash`, `--flash-app`, `--app-address`, `--flash-probe`, `--update-probe-fw`, `--manufacturer`,
  `--product`, `--boot-cmd-id`, `--boot-reply-id`, …) drive `flasher` headlessly. It also intercepts
  a hidden esptool shim flag used by frozen builds.
- **`hex/`, `firmware/`, `tools/`** are bundled data + docs resolved at runtime by `flasher`.
- **Packaging/CI:** `esp-prog2-flasher.spec` + `scripts/build.{ps1,sh}` produce a one-file
  executable via PyInstaller; `scripts/install.{ps1,sh}` fetch a released binary onto PATH;
  `scripts/run-termux.sh` runs the app from source on Termux/Android (arm64), where freezing isn't
  viable; `.github/workflows/build.yml` builds on Windows/macOS/Linux and publishes a GitHub
  Release on `v*` tags.

Two distinct flash paths: **target** (RA4M1 over SWD via pyOCD — bootloader `.hex` and application
`.bin`) and **probe** (ESP32-S3 over its ROM download port via esptool) — kept separate throughout.
