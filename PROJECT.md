`esp-prog2-flasher` (v3.0.0) is a `uv`-managed Python TUI/CLI for flashing Normal Corporation boards. It does five jobs:

- **RA4M1 bootloader** (UNO R4 Minima), flashed over SWD through an ESP-Prog-2 with **pyOCD**. It can also write a device config block into the target's data flash: custom USB DFU manufacturer/product names plus a per-device bootloader CAN ID pair.
- **RA4M1 application** `.bin`, written to the app region (`0x4000`, or `0x8000` for the Embassy bootloader).
- **PSoC 6 full image** for the IDU Radar (PSoC 62S3 / CY8C6245), bootloader + App1, over the same SWD link.
- **SOLO ODU/IDU ESP32-S3 boards**, set up over their own USB port with **esptool**. It writes the Embedded-CAN-Bootloaders bundle plus a `cancfg` image (config block + board profile), and can provision or read a CAN node's `cancfg` alone.
- **ESP-Prog-2 firmware**, the probe's own ESP32-S3 image, reflashed with esptool.

## Architecture Overview

The package is layered so the flashing logic has **no UI dependency**:

- **`flasher.py`** is the engine.
  - **Probe detection:** finds the ESP-Prog-2 CMSIS-DAP probe by VID `0x303A`/PID `0x1002` and opens a pyOCD session per call. It halts and reads the PC to tell a blank target from a programmed one (`_detect_target`, shared by `detect` and `detect_psoc6`).
  - **RA4M1** (`r7fa4m1ab`, resolved offline from the bundled slim RA_DFP pack):
    - programs a `.hex` via `FileProgrammer`;
    - optionally writes a DFU config block to data flash `0x40101C00`;
    - with `flash_app()`, programs a raw application `.bin` at `APP_BASE_ADDRESS = 0x4000`, using sector erase so the bootloader below is preserved.
  - **PSoC 6** (`cy8c6xx5`, built into pyOCD): `psoc6_flash_segments()` keeps only main flash (`0x10000000–0x10080000`) and drops Cypress metadata. Anything else (SFLASH, eFuse) is refused before any hardware is touched.
  - **esptool** runs as a subprocess, or through a shim in frozen builds. It handles:
    - the ESP-Prog-2's own firmware (`flash_probe`);
    - CAN node `cancfg` provisioning and read-back (`provision_node`, `read_node_config`), with the offset taken from the node's partition table;
    - the SOLO path: `fetch_solo_bundle` (`gh release download`), `load_solo_bundle` (manifest checks) and `flash_solo`. `flash_solo` does one write of bootloader, partition table, otadata, updater and the 4 KB cancfg image, reads cancfg back, optionally writes an `ota_0` app, then reboots with a separate, tolerant watchdog-reset call.
  - `list_serial_ports()` feeds the SOLO port picker. Only the running bridge (`303A:1002`) is flagged as the ESP-Prog-2, because in download mode it shares `303A:1001` with every ESP32-S3.
- **`dfu_config.py`** encodes and decodes the frozen 80-byte v2 DFU config block, which must stay in lockstep with the bootloader.
  - **Contents:** manufacturer/product names and a per-device bootloader CAN ID pair (`0xFFFF` = unset).
  - **Device table:** `DEVICE_CAN_IDS` is the single source of truth for known devices and their fixed CAN ID pairs, including `SOLO ODU Controller` 0x05/0x06 and `SOLO IDU Controller` 0x07/0x08.
- **`board_profile.py`** encodes the 24-byte ESP32 board-profile record at `cancfg + 0x50`: TWAI pins, bitrate and hold-LOW GPIO mask.
  - It builds the 4 KB cancfg image (config block + record + `0xFF` pad).
  - It owns the `SOLO_PROFILES` presets: ODU on `node-4MB`, IDU on `idu-16MB`.
  - The record is a frozen contract with the ESP32 bootloader/updater.
- **`app.py` + `tui/`** form a **Textual** dashboard modelled on TTSSH.
  - **Layout:** a header with probe/serial/target state; a Targets tree (RA4M1, PSoC 6, SOLO presets, ESP-Prog-2) plus session-only Recent runs; a Details pane (hidden below 80 columns); a status line and a one-row hint footer.
  - **Keys:** typing filters the list, and `/` opens a popup of the commands valid for the selection. `tui/commands.py` is the single command table for the popup, the details pane and help.
  - **Wizards:** `enter` runs a step-by-step wizard (`tui/flows.py` + `tui/wizard.py`) ending in a `y`/`n` confirm summary, then a run view.
  - **Threading:** `app.py` owns state and runs every job in thread workers. It calls `flasher` only, never USB/serial directly.
- **`cli.py`** is the single entry point. A bare run launches the TUI, and flags drive `flasher` headlessly:
  - target detect and flash: `--detect` [`--psoc6`], `--flash`, `--flash-psoc6`, `--flash-app`;
  - probe firmware: `--flash-probe`, `--update-probe-fw`;
  - CAN node config: `--provision-node`, `--read-node-config`;
  - SOLO boards: `--flash-solo [odu|idu]` with `--bundle`/`--bundle-tag`/`--app`/`--migrate-stock`.
  
  It also intercepts a hidden esptool shim flag used by frozen builds.
- **`hex/`, `packs/`, `firmware/`, `tools/`** are bundled data and docs that `flasher` resolves at runtime. **`docs/images/`** holds the README screenshots.
- **Packaging/CI:**
  - `esp-prog2-flasher.spec` + `scripts/build.{ps1,sh}` produce a one-file executable via PyInstaller.
  - `scripts/install.{ps1,sh}` fetch a released binary onto PATH.
  - `scripts/run-termux.sh` runs from source on Termux/Android (arm64).
  - `.github/workflows/build.yml` builds on Windows/macOS/Linux and publishes a GitHub Release on `v*` tags.

The flash paths stay separate throughout:

| Path | Link | Tool | What it writes |
|---|---|---|---|
| Target | SWD | pyOCD | RA4M1 bootloader/app, PSoC 6 image |
| SOLO / CAN node | the board's own USB | esptool | updater bundle + cancfg |
| Probe | the ESP-Prog-2's ROM download port | esptool | the probe's own firmware |
